# TVAPLAY

**TVAPLAY** — IPTV-платформа с backend на Go, веб-интерфейсом телевизора на **JavaScript ES5 + jQuery 2.2.4** и отдельной административной панелью на **React**.

Репозиторий: https://github.com/unidiag/tvaplay

> **Ключевой принцип:** телевизионный интерфейс должен работать на старых Smart TV, включая LG webOS 2.0 / старый WebKit. React используется для админки, но не для TV UI.
>
> **О состоянии JWT:** ниже описана согласованная целевая архитектура, обсуждавшаяся при доработке авторизации. Публичный базовый коммит `b372481122b32c45c6612ea6ccf9a7715ca96ddb` (версия **26.18**, `BUILD_DATE=2026-10-25`, `BUILD_TIME=23:21:12`) ещё не подтверждает внедрение всех изменений. Перед релизом сверяйте этот документ с рабочим деревом и тестами.

## Возможности

- IPTV-плейлисты **M3U**, **EPG/XMLTV**, HLS reverse proxy.
- Серверные проверки доступа, включая IP/GeoIP.
- Интеграция с **Media Station X (MSX)**.
- Телевизионный UI, рассчитанный на пульт и ограниченные возможности браузера.
- React-панель администрирования.
- JSON API через `POST /api` с полем `op`.
- Авторизация по SMS с JWT access/refresh-сессиями (целевой сценарий).
- Поддержка независимых сессий на нескольких устройствах (целевая модель).

## JWT-авторизация

### Принципы

1. **SMS-код** подтверждает личность и разрешает создать сессию.
2. **Access JWT** предназначен для защищённых API-вызовов; целевой TTL — **10 минут**.
3. **Refresh JWT** предназначен только для получения нового access JWT; целевой TTL — **14 дней**.
4. **`User` не хранит полный JWT.** Учётная запись пользователя не равна конкретному устройству или его сессии.
5. **`UserRefreshToken` хранит серверную refresh-сессию** (`UserID`, `JTI`, `ExpiresAt`, IP, User-Agent и, после миграции, UID устройства).
6. **Каждое устройство имеет собственный UID**, а каждая refresh-сессия — собственный **JTI**. Один пользователь может иметь несколько устройств и сессий.
7. Клиент сохраняет выданные токены и при повторном запуске проверяет/обновляет их; одно наличие токена в хранилище **не** означает успешной авторизации.

### Схема входа по SMS

```text
TV / Browser                   Go API                        MySQL
     |                            |                            |
     |---- запрос SMS ----------->|                            |
     |<--- SMS отправлен ---------|                            |
     |---- подтверждение кода --->|---- проверка кода --------->|
     |                            |---- обновление User ------->|
     |                            |---- UserRefreshToken ------>|
     |<-- access + refresh JWT ---|                            |
     |---- authMe (Bearer) ------>|---- проверка JWT/User ----->|
     |<-------- user/OK ----------|                            |
     |       открыть main         |                            |
```

Ожидаемый ответ на успешное подтверждение SMS (пример контракта, фактические имена операций сверять с кодом):

```json
{
  "status": "OK",
  "access_token": "<access-jwt>",
  "refresh_token": "<refresh-jwt>",
  "user": { "status": 1 }
}
```

**Атомарность:** запись refresh-сессии должна быть успешно сохранена до отправки `refresh_token` клиенту. Ошибка БД не должна приводить к выдаче токена, у которого нет действующей серверной сессии.

### JWT Claims

```go
type Claims struct {
    UserID uint   `json:"uid"`
    Status uint   `json:"status"`
    Type   string `json:"type"` // "access" или "refresh"
    jwt.RegisteredClaims
}
```

| Поле | Назначение |
| --- | --- |
| `uid` | **ID пользователя** (`User.ID`), а не TVAPLAY Device ID |
| `type` | `access` или `refresh` |
| `sub` | Строковое представление `User.ID` |
| `jti` | Уникальный идентификатор выданного JWT |
| `iat`, `exp` | Время выдачи и истечения |
| `status` | Статус на момент выдачи; для актуальных прав читать `User` из БД |

**Важно:** `Claims.UserID` сериализуется как `uid`, но это *не идентификатор устройства*. Для ясности различайте `user_id`, `device_uid` и `jti` в документации и БД.

- `issueAccess()` выдаёт `type=access`.
- `issueRefresh()` выдаёт `type=refresh`.
- `getAuthUser()` принимает **только access JWT**.
- `authRefresh` и `authLogout` проверяют **только refresh JWT** и связанную запись серверной сессии.
- `parseToken()` должен проверять подпись (HS256), срок действия и обязательные claims; специализированные функции проверяют тип токена.
- JTI генерируется криптографически стойким источником случайности.

### Хранение на устройстве

Для старых Smart TV предложено использовать `localStorage` с проверкой доступности через `try/catch`:

```javascript
// ES5 only
var ACCESS_KEY = 'tvaplay_access_token';
var REFRESH_KEY = 'tvaplay_refresh_token';

function storageGet(key) {
    try { return window.localStorage.getItem(key); }
    catch (e) { return null; }
}

function storageSet(key, value) {
    try {
        if (value) { window.localStorage.setItem(key, value); }
        else { window.localStorage.removeItem(key); }
        return true;
    } catch (e) { return false; }
}
```

Это **компромисс совместимости**, а не защищённое от XSS хранилище. Refresh-токен, доступный JavaScript, может быть украден при XSS. Предпочтительнее HttpOnly/Secure/SameSite-cookie там, где браузер и схема развёртывания позволяют использовать их надёжно. Не записывайте JWT в логи, URL и аналитические события. Используйте HTTPS.

### Поведение после F5 / повторного запуска

```text
init()
  |
  +-- нет сохранённых токенов ----------> login
  |
  +-- есть access ----------------------> authMe
  |                                          |
  |                                      успешен -> main
  |                                          |
  |                                  истёк / 401
  |                                          v
  +-- есть refresh --------------------> authRefresh
                                             |
                                         новый access
                                             |
                                           authMe
                                             |
                                             main
```

- При истечении access JWT необходимо вызвать `authRefresh`, сохранить новый access JWT и повторить авторизованный запрос.
- Если refresh JWT истёк, отозван или неверен — удалить локальные токены и показать SMS-вход.
- **Сетевые ошибки не означают отзыв сессии**: не очищать токены при timeout/offline, а показать ошибку сети и возможность повторить попытку.
- При обновлении страницы не открывать `login` без попытки восстановить сессию.
- При явном выходе вызвать `authLogout` для отзыва серверной refresh-сессии и удалить локальные токены.
- Для нескольких параллельных 401 желательно объединять вызовы refresh в один запрос (single-flight), чтобы избежать гонок.

### API-операции авторизации

Общий способ обращения: `POST /api`, операция передаётся полем `op`. Ниже приведены **логические** операции; фактический транспортный формат, имена SMS-операций и структура ответа определяются действующим `api.go`.

| Операция | Назначение | Ожидаемый результат |
| --- | --- | --- |
| Подтверждение SMS (`guestConfirmcode` в обсуждавшемся коде) | Проверка SMS, создание access/refresh | `access_token`, `refresh_token`, `user` |
| `authMe` | Проверка access JWT | `status=OK`, `user` |
| `authRefresh` | Проверка refresh JWT и записи БД | Новый `access_token` |
| `authLogout` | Отзыв refresh-сессии | `status=OK` |
| `authLogin` (если используется) | Вход по паролю | Должен соблюдать ту же модель сессий |

Access передаётся в HTTP-заголовке:

```http
Authorization: Bearer <access-jwt>
```

Refresh передаётся на `authRefresh`/`authLogout` в предусмотренном API поле `refresh_token`, **не вместо access в Bearer**.

## Данные: пользователь, устройство, сессия

### `User`

`User` — одна учётная запись: телефон/логин, статус, пароль (если вход по паролю сохранён), SMS-поля, даты активности. Поле `User.Token` в исходной схеме используется для подтверждения регистрации/смены пароля и **не должно хранить JWT**.

**Целевая модель:** удалить `User.UID` **только после** переноса всей бизнес-логики и данных. Не удаляйте его автоматически при добавлении UID в другую таблицу.

### `UserRefreshToken`

Минимальные поля сессии (сохраняйте и остальные поля текущей модели):

```go
type UserRefreshToken struct {
    ID        uint      `gorm:"primaryKey"`
    UserID    uint      `gorm:"not null;index"`
    UID       string    `gorm:"size:36;index"` // device UID: после миграции
    JTI       string    `gorm:"size:64;uniqueIndex;not null"`
    ExpiresAt time.Time `gorm:"not null;index"`
    UserAgent string    `gorm:"type:text"`
    IP        string    `gorm:"size:45"`
    CreatedAt time.Time
}
```

`UID` **не должен иметь unique-ограничение**, если допускаются повторные сессии одного устройства. `JTI` — уникальный идентификатор сессии/refresh JWT. При переавторизации устройства можно отозвать его прежние refresh-сессии, не затрагивая другие устройства.

Если устройство должно оставаться зарегистрированным после выхода/истечения refresh JWT (настройки ТВ, привязка, активация, история), используйте отдельный `UserDevice`: `User 1:N UserDevice 1:N UserRefreshToken`. Хранить долгоживущую идентичность устройства **только** в таблице временных сессий в таком случае недостаточно.

### Миграция UID: безопасный порядок

1. Сделать резервную копию БД.
2. Определить, где используется `User.UID`: SMS API, handshake, проверка активации, клиентские запросы, админка, EPG/playlist и MSX.
3. Добавить `UID` в `UserRefreshToken` (или создать `UserDevice`, если нужен постоянный реестр).
4. Передавать UID текущего TV при создании сессии; валидировать формат и принадлежность.
5. Перенести необходимые исторические значения. Для уже существующих сессий без UID определить явную политику (например, повторная SMS-авторизация).
6. Обновить чтение UID во всех обработчиках и тестах.
7. Только затем удалить `User.UID` и колонку из БД. **GORM AutoMigrate сам по себе не является планом удаления колонки.**

Device UID — клиентский идентификатор, а не секрет и не самостоятельное доказательство авторизации. Нельзя предоставлять доступ только по UID.

## Безопасность JWT и SMS

- JWT signing secret должен быть длинным, случайным и храниться **в конфигурации/окружении**, а не в Git.
- После смены секретного ключа старые JWT перестают проходить проверку; продумайте сценарий повторного входа.
- Не используйте общий пароль вроде `1234` как обход SMS для пользовательских учётных записей; отключите такой вход или обеспечьте полноценную проверку индивидуального пароля и ограничение попыток.
- Ограничивайте частоту отправки SMS и попыток ввода кода, храните дату истечения и счётчик попыток.
- Защищайте `authRefresh` и `authLogout` от подмены типа токена; сверяйте `jti` и `user_id` с БД.
- Защищайте refresh-токены от утечек. В долгосрочной архитектуре желательно хранить их односторонние отпечатки / JTI и поддерживать rotation/revocation; текущий проект требует проверки семантики обновления.
- Не считайте `status` в JWT вечно актуальным: для чувствительных операций проверяйте состояние пользователя в БД.
- Используйте HTTPS, разумные CORS-настройки, безопасные HTTP-заголовки и строгую обработку недоверенного HTML в jQuery.

## Телевизионный JavaScript и сборка

Исходники TV UI размещаются в `frontend/public/app/js/`, файлы именуются `NN-name.js`, объединяются **в лексикографическом порядке** и доступны в виде `/app/main.js`. Пример цепочки авторизации:

```text
frontend/public/app/js/
├── 03-api.js          # HTTP API, хранение JWT, refresh
├── 30-loginPage.js    # SMS и сохранение токенов
└── 99-app.js          # init и восстановление сессии
```

Это имена модулей из обсуждавшихся изменений: сверяйте их с фактическими файлами рабочего дерева.

- **Debug:** чтение модулей с диска, склейка на запрос, без обязательной минификации.
- **Production:** встроенные Go-ресурсы, склейка, минификация и кеширование.
- Минификация **не транспилирует** современный JavaScript в ES5. Не используйте `let`, `const`, стрелочные функции, `async/await`, optional chaining и современные API без проверки.
- Весь доступ к `localStorage` оборачивайте в `try/catch`; часть браузеров Smart TV может блокировать запись.
- `main.css` размещён в `frontend/public/app/main.css`. Отдельный обработчик CSS-минификации требует проверки в коде.

### Версионирование и кеширование ресурсов

Оба ресурса должны получать одинаковую версию в query-параметре:

```html
<link rel="stylesheet" href="/app/main.css?v=VERSION">
<script src="/app/jquery-2.2.4.min.js"></script>
<script src="/app/main.js?v=VERSION"></script>
```

Здесь `VERSION` — условное обозначение: сервер подставляет фактическую константу из `main.go` (для debug — временную метку). Увеличивайте версию при изменениях TV JS/CSS, иначе старый TV может оставить закешированный модуль авторизации.

## Сборка и запуск

Требования: Go согласно `go.mod` (в базовой документации — Go 1.26), Node.js/npm для React и настроенная MySQL.

```bash
# Разработка
go run .

# Полная сборка (предварительно проверьте скрипт)
./make
```

**Осторожно:** скрипт `make` проекта может обновлять `VERSION` и дату сборки, собирать frontend/Go и **перезапускать systemd-сервис**. Не запускайте на рабочем сервере без проверки. Убедитесь, что новые TV-модули попали в ресурсы, встраиваемые через `go:embed`.

## Регрессионное тестирование JWT

- [ ] После корректного SMS сервер отвечает `access_token` **и** `refresh_token`.
- [ ] В БД создаётся `UserRefreshToken` с `UserID`, уникальным `JTI`, `ExpiresAt` и UID устройства (после миграции).
- [ ] `authMe` с access JWT работает; с refresh JWT возвращает ошибку.
- [ ] `authRefresh` с refresh JWT работает; с access JWT возвращает ошибку.
- [ ] Оба токена сохраняются в клиентском хранилище при поддержке `localStorage`.
- [ ] После F5/restart TV без повторного SMS открывается авторизованный экран.
- [ ] После истечения access JWT выполняется refresh и `authMe`.
- [ ] После истечения/отзыва refresh JWT запрашивается повторный SMS.
- [ ] При кратковременном обрыве сети локальные токены не стираются.
- [ ] У одного пользователя работают две независимые сессии на разных TV.
- [ ] Logout одного TV не удаляет сессию другого TV.
- [ ] Проверены гонки параллельного refresh и повторная авторизация на том же UID.
- [ ] На реальном старом Smart TV работают `localStorage`, ES5, навигация пультом и повторный вход из MSX.
- [ ] В production после релиза отдаются **новые** `main.js` и `main.css`.
